# Governance, Channel Types & Voting Design — share-context-mcp

Date: 2026-10-28
Status: Pending approval
Scope: Roles (creator/manager), three channel trust tiers, token lifecycle,
generic vote module (kick v1), CLI/MCP surface split, multi-channel tooling.
Supersedes parts of 2026-10-28-session-identity-and-history-design.md (rotate
moves out of MCP; kick model replaces "rejoin-under-new-name is accepted").

## Intent & Why

Password channels make everyone equal: anyone with the token can rotate, kicks
don't stick (shared password = rejoin under a new name), and dangerous
operations sit on the agent-facing tool surface. This iteration adds real
governance:

- **Creator / manager roles** with succession rules.
- **Three channel trust tiers** (public / invite / password) with a universal
  per-member token model so kick = token ban, uniformly.
- **A generic vote module** on the relay (v1 action: kick), thresholds and
  cooldowns as specified by the product owner.
- **A CLI/MCP split principle**: low-frequency and dangerous operations live in
  the CLI (human-in-the-loop); the MCP surface stays safe-by-default.
- **Multi-channel ergonomics**: per-session channel ledger, `list_channels`,
  and a `channelId` echo in every tool response.

## Goals / Non-goals / Anti-goals

- **Goals**: enforceable roles; kicks that actually remove a member; human
  decisions for destructive ops (CLI); agents can perceive votes and cast
  ballots; multi-channel sessions without identity confusion.
- **Non-goals**: forward secrecy; per-message signatures (provenance stays
  self-declared this iteration); anonymous voting; relay-side content
  moderation.
- **Anti-goals**: breaking the blind relay for password channels; making the
  agent able to revoke human access.

## Approaches Considered

### Kick enforcement in password channels
- **A. Invite-style relay-held keys** — rejected for password tier: the relay
  would hold/decrypt password-channel content, breaking the E2E promise.
- **B. Auto re-key on kick (HKDF-coupled)** — rejected twice over: remaining
  members cannot learn the new message key without out-of-band redistribution,
  and it deafens the rest.
- **C. Token-ban kick + automatic admission-credential rotation (chosen)**
  with the UNIFIED self-contained credential (owner refinement): the message
  key is random at creation and travels wrapped INSIDE the admission
  credential — it never derives from the password. Kick revokes tokens, bans
  name/consumer ids, then rotates the admission CREDENTIAL only: same message
  key re-wrapped under a new wrapping secret. Remaining members already hold
  the message key — zero disruption, zero redistribution. The kicked member's
  old credential is dead, so re-entry under a new name is closed outright.
  Optional hardening: IP ban (vote option) and the invite-gate switch.

### Credential unification: password vs invite code
- **Chosen: same self-contained mechanism, different sharing granularity.**
  The admission credential is generated by the manager/creator's client (it
  wraps the message key — only a key-holder can mint it) and contains the
  verify-hash (relay-visible) plus the wrapped message key (opaque).
  - **password mode**: one shared credential, unlimited use; generated and
    reset by manager/creator ONLY.
  - **invite mode**: per-member, single-use codes plus the lineage graph
    (who invited whom) and relationship-based freezes/bans. **Invite policy**
    (manager/creator setting): `everyone` (default — any member with
    `can_invite` may mint codes) or `managers-only` (only manager/creator
    mint codes).
  - **Admission mode is switchable** (manager/creator, CLI, audit-logged) and
    affects FUTURE admissions only: existing members, tokens, and the message
    key are untouched. Switching to public is a privacy downgrade (the relay
    holds the key for new messages) — CLI double-confirm.

### Vote tallying location
- **Chosen: relay-side** — votes/ballots/thresholds/cooldowns are relay
  metadata and state; enforcement (ban, revoke) is relay's job anyway. Local
  servers only render (own OS timezone).
- Local-consensus tallying rejected: no authoritative enforcement point, races
  and trust issues.

### Authentic per-member message statistics
- **Chosen: relay records `sender` on each stored message** (the POST is
  token-authenticated — attribution is real, not self-declared). Cost: the
  relay can build per-member send-volume profiles. Accepted: the threat model
  already concedes traffic analysis; without this the required statistics
  (totals, per-day shares) would rest on forgeable self-reported provenance.

## 1. Channel Trust Tiers

| | **public** | **invite** | **password** |
|---|---|---|---|
| Admission | none | invite code (single-use, per-member, lineage recorded) | password (challenge-response) |
| Message key | relay-generated, relay-held | random at creation, delivered self-contained inside invite codes; **relay never holds it** | random at creation, self-contained inside the admission credential; **relay never holds it; never derives from the credential** — credential rotation re-wraps the SAME key |
| Relay visibility | transport-only encryption; relay can decrypt | metadata + lineage; cannot decrypt content | fully blind |
| Kick | token ban + name + consumer-id blacklist (+ optional IP ban) | token ban; rejoin requires a fresh code from a member (cannot self-invite) | token ban + name/consumer-id blacklist + **auto admission-password rotation** (new password to manager/creator only) — the kicked member cannot re-enter even under a new name |
| Hard re-key | trivial (relay re-issues) | new codes only (gate change); message-key change needs manual redistribution | full rotate (CLI, two modes, below) |
| Join-time records | name, joined_at, ip | name, joined_at, inviter, ip | name, joined_at, ip |
| Directory listing | listed by default | opt-in (manager sets contact info) | opt-in (manager sets contact info) |
| Admission mode | switchable by manager/creator (future admissions only; audit-logged) | same | same |

All three tiers issue the same per-member **token pair** at admission
(section 3); kick = token ban works uniformly. In public/invite tiers a ban is
final in practice (admission is not password-gated or is code-gated); in the
password tier, kick additionally auto-rotates the admission password (new
password disclosed to manager/creator only), so the kicked member cannot
re-enter under any name. Optional hardening: IP ban (vote option; NAT caveat)
and the invite-gate switch ("joins require password AND a valid code" — flips
on automatically after the first successful kick-vote, or manually by the
manager).

## 2. Roles & Succession

- `creator_member` — immutable, EXCEPT when the creator is kicked: the role
  passes to the vote initiator (if the initiator is already the manager, they
  hold both roles).
- `manager_member` — mutable; day-to-day admin: rotate (CLI), invite-gate
  toggle, directory listing/contact info.
- Initial state: manager = creator.

| Event | creator | manager |
|---|---|---|
| manager kicked | unchanged | **vote initiator** |
| creator kicked | **vote initiator** | unchanged |
| creator leaves | transfer (see below) | unchanged (creator had to leave last anyway unless transferring) |
| manager leaves (not creator) | unchanged | **reverts to creator** |
| last member leaves | **channel dissolved** | — |

**Creator leave** (CLI): either names a successor (must be an active member) or
omits it → default rule: most messages in the trailing 7 days among current
members excluding the creator (must have ≥1 message in that window, else
skip) → tie-break: earliest joined → if no one qualifies: earliest joined
member overall. Leaving member's data (tokens) revoked; membership row kept
with status `left` (name cannot be reused by transfer target ambiguity —
freed after the normal TTL rules).

**Dissolution**: last ACTIVE member leaving (any role) deletes the channel at
the relay: channels row, members, messages, votes, invite ledger. Subsequent
`join` with the old password/code returns 404 `channel not found`. Member
servers learn via 404 on poll → remove local state for that channel.

**Leave notifications**: `member-left` / `role-changed` metadata frames are
fanned out to online members (names only — no content). The successor notice
carries the successor's stat profile (same payload as the kick notice,
section 4).

## 3. Token Lifecycle (all tiers)

- Admission issues **one per-member, per-channel token**. Default: **no
  expiry** (TTL configurable; `1h` was rejected as too short — membership
  continuity must not depend on token churn).
- **Relay validation is a triple**: `(channel, consumer_id, token)` — a token
  is only valid for its channel, and only for the consumer_ids registered
  under that membership (banned consumer ids are rejected). Implementation
  refinement: an UNKNOWN consumer id presented with a valid member token is
  auto-registered (the token IS the membership proof — multi-session
  processes must just work); the ban list is the enforcement point. Tokens
  are not portable across channels.
- **CLI `token refresh`** rotates the token (old one invalidated, new one
  issued) — the user's self-service move when a token may have leaked.
- **Every message send carries the sender's consumer_id**; the relay validates
  it against the registered set for the authenticated member — the sender
  identity is checked on every write, not just at admission.
- **Every channel API validates the token first**; the only token-less
  endpoints are the admission ones (challenge, join, create, public directory
  info). Token-authenticated endpoints additionally validate the request's
  consumer_id (registered for this member, not banned) — admission checks the
  identity ONCE, every subsequent write/read checks it EVERY time.
- Kick: token revoked atomically; member status → `banned`; name enters the
  channel blacklist; re-challenge with that name is rejected.
- Optional IP ban (vote option): rejected connections from the recorded IP for
  this channel. Caveat surfaced in CLI: shared office NAT can over-block.

## 4. Generic Vote Module (relay-side, v1 action: kick)

```
votes(id, channel_id, type, initiator, target, params_json,
      started_at, ends_at, status: open|passed|failed)
ballots(vote_id, voter_name, choice)            -- one ballot per member
channels: vote_cooldown_until, last_vote_at      -- single open vote per channel
member_bans(channel_id, name, consumer_ids[], ip?, banned_at)
member_consumer_ids(channel_id, member_name, consumer_id, last_seen)
```

- **Initiation: CLI only** (`share-context vote start --channel X --type kick
  --target N [--reason] [--ban-ip]`). Requirements: ≥3 active members, no open
  vote, initiator not in cooldown, target is an active member ≠ initiator.
- **Voting: MCP** (`cast_vote(voteId, choice)`), one ballot per member; the
  target cannot vote. `fetch_updates` responses carry an `openVotes` array
  (vote id, type, target, deadline) so agents can perceive and act.
- **Thresholds** (as specified, with the agreed guardrails):
  - target is manager or creator: `yes ≥ 2/3 of cast ballots` AND `cast ≥ 1/2
    of active members` (turnout floor).
  - target is a regular member: `yes > 1/2 of cast ballots`.
  - Abstentions (no ballot) are excluded from the denominators.
- **Early resolution**: the vote settles the moment the outcome is
  mathematically decided; otherwise it settles at 48h.
- **Cooldowns**: after any vote ends, the channel enters a 4h global cooldown
  (no new vote). The initiator of a PASSED vote cannot initiate again for 48h;
  of a FAILED vote, for 7 days.
- **Kick action — token ban + automatic admission-credential rotation
  (password tier)**: revoke the token, blacklist the name and every observed
  consumer_id, then the relay **auto-rotates the admission credential**. The
  new credential is disclosed ONLY to the manager/creator (CLI, printed once)
  — remaining members never need it: their valid tokens carry their
  membership, and the message key (held by every member since their own
  admission) is untouched. Because the old credential is dead, the kicked
  member cannot re-enter even under a NEW name — this closes the
  shared-credential re-entry hole outright.
- **Kick action — invite tier**: revoke tokens + blacklist name/consumer ids.
  **Surgical code disposition** (no scheme-wide rotation): the invite code the
  target USED to join is revoked, and its OWNER (the inviter) is notified to
  mint a fresh one — the replacement is generated by the owner's own client
  (self-contained code carries the channel key; the relay stays blind and
  cannot mint it). If the owner is no longer an active member, the code slot
  simply dies. Remaining members' codes are untouched — everyone keeps their
  invite capability.
- **Invite-right model (invite tier)**: `can_invite` per member (default true)
  + channel-level `invite_policy` (manager/creator setting): `everyone`
  (default — any member with `can_invite` may mint codes) or `managers-only`
  (only manager/creator mint codes). Effective mint right =
  `can_invite AND (policy == everyone OR is manager/creator)`.
  **Revocation (vote option)**: `--revoke-invitees` — when the kick passes,
  every member the target INVITED loses their invite right
  (`can_invite = false`; manager/creator excluded from automatic revocation
  for governance continuity): their existing codes are invalidated and they
  are notified explicitly ("your invite right has been revoked"). They remain
  full members otherwise (read/write unaffected). The relay rejects any
  code-mint/invite attempt from a member without the effective right.
  Restoration: manager/creator via CLI (`channel grant-invite`), which also
  re-enables minting a fresh code.
- **Lineage freeze**: when a kick vote OPENS, the target's invite code and the
  invite codes of everyone the target invited are frozen for the duration of
  the vote; if the vote PASSES the target's code stays revoked, the invitees'
  codes stay banned until 7 days after settlement (then auto-expire; the
  manager can extend); if it FAILS the freeze is lifted automatically.
- **Kick action (continued)**: `role-changed` broadcast if succession fired;
  kick + succession notices carry the stat profile (below).
- **Notification payload** (structured, relay-side; rendered locally in each
  server's OS timezone): target name, joined_at, total messages + share of
  channel total, last-active time, per-day counts for the trailing 7 days +
  share of that day's channel total, role badge, and — when the target is the
  manager — the successor's identity plus the same stat profile for the
  successor.
- **Future vote types**: new `type` entries register a relay-side action;
  `params_json` carries type-specific (metadata-only) parameters. The schema
  above does not change.

## 4c. Invite Codes & Admission Credentials (invite/password tiers) — lifecycle

- **Admission credential (password tier)**: generated/reset by the
  manager/creator's client ONLY (self-contained; carries the wrapped message
  key). Shared, unlimited use. Distributed out-of-band.
- **Invite code (invite tier) — mint**: by the owner via MCP (`mint_invite`)
  or CLI (`share-context invite <id> [--ttl <duration>]`), **subject to the
  invite-right model** (§4, `can_invite` × `invite_policy`). Default TTL:
  **7 days** (configurable per mint; optional no-expiry flag for trusted
  settings). Self-contained; single-use; lineage recorded
  (`invite_id → owner`).
- **Regenerate**: owner invalidates the current code and mints a fresh one
  (new TTL). The old code dies immediately — anyone holding it is rejected
  with an explicit reason.
- **Cancel**: owner invalidates the code. Same rejection behavior.
- **Expiry**: enforced at the relay at join time — expired/cancelled codes
  return 403 `invite code expired or cancelled`.
- **Admission credential reset** (`rotate --mode access`, §5) and **mode
  switching** (`set-admission`) are manager/creator operations.
- Mint/cancel are owner-scoped self-service (they never affect existing
  members); manager/creator additionally manage invite RIGHTS of others
  (`revoke-invite` / `grant-invite`, §5) and the invite policy.
- Both mint and cancel are owner-scoped self-service (they never affect
  existing members); manager/creator additionally manage invite RIGHTS of
  others (`revoke-invite` / `grant-invite`, §5).

The relay records every governance operation for later inspection:
admission (join/invite-used), leave, kick votes (opened/ballot/settled +
outcome), bans and unbans, role changes, admissions-password rotation,
dissolution. Each entry: timestamp, actor (member name), action, target,
and result. Queries via CLI (`share-context audit <id>`) with member
credentials — governance transparency for every member, not just the
manager.

## 4b. Audit Log

The relay records every governance operation for later inspection:
admission (join/invite-used), leave, kick votes (opened/ballot/settled +
outcome), bans and unbans, role changes, admissions-credential rotation,
admission-mode switches, dissolution. Each entry: timestamp, actor (member

## 5. CLI / MCP Surface Split (principle: dangerous & low-frequency → CLI)

**CLI (human-in-the-loop)**:

```
share-context channel list / info <id>        # session ledger / full member+role state
share-context channel bans <id>               # banned members: name, consumer_ids, ip,
                                              # banned_at, banned by (member/vote ref)
share-context channel unban <id> --name N     # restore entry rights (manager/creator);
                                              # clears name + consumer_ids + ip bans
share-context channel revoke-invite <id> --name N   # strip a member's invite right
                                              # (manager/creator); member is notified
share-context channel grant-invite <id> --name N    # restore a member's invite right
                                              # (manager/creator); re-enables minting
share-context channel transfer <id> --to NAME # creator handover (explicit)
share-context channel dissolve <id>           # explicit dissolve (also implicit on last leave)
share-context channel set-admission <id> --mode public|password|invite
                                              # [--invite-policy everyone|managers-only]
                                              # [--contact "..."]  (manager/creator;
                                              # affects future admissions only; public
                                              # switch double-confirms: relay-readable
                                              # for new messages; audit-logged)
share-context rotate <id> --mode access|full  # access: password only (members
                                              # unaffected); full: + message key
                                              # (prints "N members need the new
                                              # password" warning)
share-context invite <id>                     # invite channels: emit code
share-context token refresh <id>
share-context vote start --channel X --type kick --target N [--reason] [--ban-ip]
share-context vote list [id]                  # full history + tallies
share-context audit <id>                      # governance audit log (all members)
share-context directory [query]               # relay-side channel directory search
```

- Rotation and admission-password rotation are **manager/creator only**
  (enforced at the relay); the CLI checks and the relay rejects others.

- `unban` is manager/creator-gated. It clears the ban (name, consumer ids, IP)
  but is NOT readmission: the unbanned person still needs valid admission
  credentials (password tier: the current password; invite tier: a fresh code
  from a member). In password tier, unbanning re-opens the shared-password
  rejoin door for that person — the CLI prints this reminder.

- `rotate --mode access` (default): re-wraps the SAME message key under a new
  admission credential — members are unaffected (they already hold the
  message key); only future admissions use the new credential. Zero
  disruption.
- `rotate --mode full`: new admission credential AND a NEW message key;
  remaining members must apply the printed member-update code via CLI
  (`rotate-accept`) — the CLI prints the count and a warning. In invite
  channels, `full` is not offered (the relay holds no key); `access`
  re-issues codes.

**MCP (agent-facing)**:

```
share_update, fetch_updates, catch_up, search_messages,
set_subscription, list_members, create_channel, join_channel,
leave_channel, cast_vote, list_channels
```

- `leave_channel` stays in the MCP surface for ALL members (creator included):
  the creator's call accepts an optional `transferTo`; omitting it applies the
  default succession rule; the last active member leaving triggers dissolve.
- `rotate_password` is REMOVED from MCP (CLI-only now — behavior change,
  documented as breaking in the next release).
- git/S3 backends: governance tools (`cast_vote`, `list_channels`,
  `leave_channel`) are not registered; instructions state basic-mode capability.

## 6. Multi-channel

- Per-session channel ledger, **persisted in SQLite**
  (`consumer_id × channel_id × joined_at`). Session resume keeps the
  sessionID → the ledger view survives agent restarts. New sessions start
  with an empty ledger by design; `join_channel` against a channel the server
  already holds requires no password (local ledger add + attach to the
  existing membership; zero relay interaction) — the empty state self-heals.
- `list_channels` (MCP): the session's ledger entries with per-channel meta
  (id, name, type, role of the member, unread count). NOT a server-wide dump.
- Directory search (`share-context directory [query]`, CLI): relay-side
  listing of channels that opted in (public by default; password/invite show
  the manager-set contact info only).
- Every MCP tool response echoes `channelId` — the agent always knows which
  channel produced the data (fixes the "forgot the id" gap).

## 7. Storage / Behavior Changes

- relay schema: `channels.creator_member, manager_member,
  vote_cooldown_until, admission_mode, invite_policy, contact_info,
  admission_credential_hash`; new tables `votes`,
  `ballots`, `member_bans`, `invite_codes`, `member_consumer_ids`,
  `audit_log`; `messages.sender`; `members.status, last_active_at,
  token_hash, can_invite`.
- server schema: `consumer_channels(consumer_id, channel_id, joined_at)`;
  member token persisted per channel (hashed); the admission credential
  (self-contained, carries the wrapped message key) is kept for password-tier
  rejoin after restart.
- MCP tool list changes (breaking): `- rotate_password`,
  `+ cast_vote`, `+ list_channels`; all responses `+ channelId`.
- Relay persistence grows (votes/bans/lineage) — all metadata, still
  content-blind for password/invite tiers.

## 8. Edge Cases

| Edge | Behavior |
|---|---|
| Creator kicks themselves via vote | Unreachable — vote open rejects `target == initiator` (divergence from the spec prose, intentional: self-kick has no counterparty to judge); creator removal happens via another member's vote |
| Vote target leaves mid-vote | Vote voided (`status=expired`), no cooldown beyond the 4h global |
| Manager leaves (not creator) | Manager reverts to creator; notice broadcast |
| Two CLI initiators race | Single-open-vote constraint: second `vote start` rejected |
| Refresh token reuse (old after rotation) | Treated as theft signal: member's tokens revoked, re-auth via admission required |
| Kicked member's server polls | 403 `banned`; server marks channel `revoked` locally, stops polling, keeps local cache (read-only history) |
| Banned member challenges under a NEW name but a resumed session | consumer_id hit on the ban list → rejected (name + consumer + IP are matched independently) |
| Kick: auto admission-credential rotation (password tier) | Remaining members unaffected (valid tokens + they already hold the message key); the new credential is disclosed to manager/creator only |
| Server restart with rotated admission credential | Rejoin via the stored member token first; credential challenge is only the fallback |
| Message send with unknown/banned consumer_id | 403 rejected — sender identity checked on every write |
| Invite vote opens | Target's code + codes of everyone the target invited are frozen while the vote is open |
| Invite vote passes | Target's used code revoked permanently; replacement minted by its owner's client (owner notified; slot dies if owner gone); invitees' codes stay banned until 7 days after settlement |
| Invite vote fails | Lineage freeze lifted automatically |
| Unban | manager/creator clears name + consumer_ids + IP; readmission still requires valid credentials (password tier CLI reminder: the current password is post-rotation — fetch it from the manager/creator) |
| Member with `can_invite = false` tries to mint/share an invite code | Rejected with an explicit reason; the member was notified at revocation time and can check status via `channel info` |
| Vote settles with `--revoke-invitees` passed | Invitees' invite RIGHT stays revoked until restored (does not auto-expire); their codes remain banned 7 days post-settlement |
| Switch admission mode to public | Future-admissions-only semantics; CLI double-confirm (relay-readable for NEW messages; old messages stay E2E); audit-logged |
| Switch admission mode with an open vote | Allowed — votes and membership unaffected; only the admission gate changes |
| Dissolved channel poll | 404; server removes local channel state |
| cast_vote on a settled vote | 409 `vote settled` |
| IP ban on shared NAT | Documented caveat; CLI double-confirm on `--ban-ip` |
| `rotate --mode full` with zero other members | No redistribution warning needed |
| Public channel kick | Weakest enforcement (anyone can re-rejoin); documented tier semantics |

## 9. Left to the Builder

- TTLs surfaced as constants and overridable via relay flags: vote 48h,
  cooldowns 4h/48h/7d. Member tokens: no expiry by default (optional TTL flag).
- `messages.sender` backfill: not possible for pre-existing rows (sender
  unknown) — stats counters start at adoption; documented.
- Notification frame shapes (keep within the blindness rules: names, ids,
  counters only).
- Test matrix: succession table (§2), threshold boundaries (2/3, 1/2, turnout
  floor), cooldown transitions, token refresh/rotation/ban flows, invite
  single-use enforcement, directory visibility opt-in, per-session ledger
  persistence across restart.

## 10. Future Extensions

- Vote types beyond kick (config changes, threshold changes) via the action
  registry.
- Invite-code expiry windows and per-code member caps.
- Signed provenance (per-member signing keys distributed via invite/password
  admission) to make statistics non-forgeable.
